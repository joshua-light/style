Animated explainer · The .NET runtime

The garbage collector never looks for garbage

It finds what is still in use and takes back everything else. Seven short films follow one small heap through the whole job: making objects, losing them, marking, compacting, growing old, and two of the runtime's stranger corners.

Film 1 / 7

A new object costs one pointer bump

C# never asks you to free memory, so it had better be cheap to take. It is. The managed heap keeps one pointer to the start of its free space, and new does little more than move it.

The budget is not fixed. The runtime tunes it as the program runs, from how much survived the last collections.

Film 2 / 7

Garbage is made by forgetting

An object is in use while the program can still get to it. The places a program can start from are called roots: the locals of every running method, and every static field. From a root it can follow references to other objects, and from those to more.

Four objects are now garbage, and the heap looks exactly as it did. No counter ticked, no flag was set. The objects themselves hold no sign that they are dead.

What else counts as a root?

Handles the runtime gives out, such as pinned objects and references held by native code. The queue of objects waiting for their finalizers, which the last film covers. And in an optimised build a local stops being a root after its last use, which can be well before its method returns.

Film 3 / 7

The collector marks the living

The dead carry no sign, so the collector cannot search for them. It does the reverse: it walks everything the program can reach, and marks it.

Predict

The film holds after the marking. Draft and Line were not reached, but each still references the other. Will the collector keep them?

Being referenced is not the test. Being reachable from a root is. A pair, or a whole ring, of objects that only hold each other is as dead as an object nothing holds. The film goes on.

The last beat is why allocation-heavy .NET code can still run fast. A wave of ten thousand short-lived objects costs the mark phase nothing if none of them survives.

Film 4 / 7

Sweeping leaves holes, and compacting closes them

Whatever is not marked can be taken back. The easy way is to sweep: walk the heap once and call every unmarked stretch free. It works, and it leaves a problem behind.

Compacting is what keeps allocation a pointer bump. It is also the costly part: every survivor is copied, and every reference to it fixed. So the runtime compacts the young heap freely and the old heap only when the holes are worth the work.

What about very large objects?

An object of 85,000 bytes or more goes to a separate large object heap. Copying such objects costs too much, so that heap is swept and not compacted by default. It can fragment in exactly the way the film shows. That is the case for reusing big buffers and not making new ones.

Film 5 / 7

Most objects die young, so the young are collected most

Marking the whole heap on every collection would waste the collector's best fact about programs: an object that has just been made will probably be dead in a moment, and one that has lasted a while will probably last longer. So the heap is split by age into three generations.

The costly object is the one in between: it lives just long enough to reach Gen 2 and dies there, where only a full collection can take it back.

Film 6 / 7

An old object can point at a young one

A Gen 0 collection is fast because it never walks Gen 2. That shortcut has a hole in it, and the runtime pays a small tax on every assignment to close it.

Predict

The film holds after the store. Suppose a Gen 0 collection now marks from the stack and never enters Gen 2. What happens to Entry?

Nothing on the stack leads to Entry. Its only holder sits in Gen 2, where this collection does not look. Freeing it would leave Cache pointing into free space. The runtime cannot allow that, and cannot afford to walk Gen 2 to prevent it. The film shows its way out.

Film 7 / 7

A finalizer buys an object one more life

A finalizer is code the runtime promises to run before an object's memory is taken back. The promise is kept in the least convenient way.

This is what Dispose() is for. It does the cleanup at once, and GC.SuppressFinalize(this) takes the object off the list, so it dies like any other.

Recap

Six statements, checked against the films

  • The collector searches the heap for garbage.False

    It marks what the roots can reach. Garbage is whatever is left.

  • Allocating is cheap.True

    A pointer bump, as long as the free space is one block.

  • Setting a variable to null frees the object.False

    It removes one path. The memory comes back at a later collection, and only if no other path is left.

  • Two objects that reference each other can never be collected.False

    True of reference counting. A tracing collector asks only whether a root reaches them.

  • More garbage makes a collection slower.False

    Marking and compacting follow the survivors. Dead objects cost almost nothing.

  • A finalizer runs when its object goes out of scope.False

    It runs some time after a collection finds the object dead, on another thread, and delays the memory by one more collection.

What it means for code

  • Short-lived objects are cheap. They die in Gen 0 and cost the collector nothing.
  • Middle-aged objects are not. Avoid keeping things just long enough to reach Gen 2.
  • A leak is a forgotten root. A static list, a cache, an event still subscribed: whatever they reach, lives.
  • Dispose; do not finalize. Keep finalizers for the rare type that owns a native resource directly.
  • Reuse big buffers. At 85,000 bytes they leave the compacted heaps.
